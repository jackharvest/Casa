The Picasa Viewer Gap on macOS

Windows got three credible Picasa Photo Viewer successors. The Mac got one abandoned F# experiment with seven stars. Here is the full landscape, the exact gap, and what it would take to fill it.

18 Sep 2026 · updated Target: macOS 26 Tahoe Working name: PicasaPreview

The short answer

Yes — exactly once, and it died. Thecentury/picasa is literally titled "A Picasa-like image viewer for macOS." It is written in F# on Avalonia + FuncUI, has 86 commits, 7 stars, 0 forks, no releases, and a TODO list that still includes "write build instructions" and "create a redistributable package." It reached navigate / rotate / delete and stopped.

Nobody else has tried. Every other Mac viewer is either a Preview replacement (minimal, opens one file) or a library manager (digiKam, Lightroom, Peakto). The thing Picasa's viewer actually was — a zero-chrome overlay that appears instantly over whatever you were doing and lets you flick through a folder without thinking — has no Mac equivalent.

What "Picasa viewer" actually means

This matters because "Picasa" gets confused with the library app. The viewer was a separate binary that Google shipped alongside it, and the nostalgia is specifically for the viewer. Its defining traits, ranked by how much they contribute to the feeling:

  1. 01Sub-100ms cold startDouble-click to photo-on-screen felt instantaneous, even on 100 MB RAW. No splash, no window chrome animation, no spinner. This is the single trait everything else hangs off.
  2. 02Borderless translucent overlayFull-screen, semi-transparent black ground, the photo floating on it, no title bar. It read as a lightbox over your desktop rather than an application window.
  3. 03Arrow keys just workLeft/right steps through the containing folder in the order the file manager showed it — with adjacent images already decoded, so holding the key scrubs instead of stuttering.
  4. 04Scroll wheel zooms to the cursorNot zoom-to-center. The pixel under your pointer stays under your pointer. Pan by drag. This is the interaction people describe when they say a viewer "feels right."
  5. 05Toggleable filmstripA thumbnail rail at the bottom, hidden by default, scrubs the folder when hovered.
  6. 06Escape / double-click dismissesIt was disposable. You opened it, looked, and it was gone. It never asked you to manage a window.
  7. 07Respects the file manager's sortIf Explorer was sorted by date, the viewer stepped by date. If you'd filtered a search, it stepped only the filtered set.

Traits 1, 2, 4 and 6 are what no Mac app currently combines. Traits 3, 5 and 7 exist in pieces.

Windows proved the demand

The Windows side of this niche is healthy, which is the useful signal: people care enough about a discontinued 2015 viewer that three separate projects target it by name.

FlyPhotos is the one you already know, and it's the benchmark worth studying. Its README states the goal outright — "a modern replacement for the now-discontinued Google Picasa Photo Viewer." The engineering choices are all in service of trait 01:

  • Native AOT compilation — no JIT warm-up on launch, which is the entire reason it starts instantly.
  • WinUI 3 + Win2D — Direct2D-backed rendering, so zoom and pan are GPU work, not CPU blits.
  • Two-tier cache — in-memory for the current neighborhood, on-disk for previews, so returning to a folder is warm.
  • "Fly-through mode" — hold an arrow key and it glides with no loading spinners, degrading to cached previews rather than blocking on full decodes.
  • Explorer integration — inherits sort order and active filters, including Recent and Search results.
  • Format coverage via the OS codec layer (Windows Imaging Component) plus explicit PSD / HEIC / AVIF / SVG / animated WebP / DDS handling.

The commercial model is worth noting too: free on GitHub, paid in the Microsoft Store for auto-updates and signing. The others in the space — ImageGlass (which has an open feature request to imitate Picasa's gestures specifically) and spica — confirm the pattern.

Nobody on macOS ships 02 + 06 + 07 together

The overlay feel, the disposability, and Finder-order fidelity. Those three are the whole product. Everything in column 03 is table stakes that six apps already have — building another arrow-key viewer adds nothing.

Trait 07 is completely unclaimed on macOS. Not one app does it. It's also the least obvious and the most differentiating: if you've sorted a folder by date-added and hit an image, stepping alphabetically is quietly wrong every time, and nobody has fixed it.

macOS constraints you have to design around

Four platform realities shape the product more than any feature choice. Two of them are why the Windows approach can't be copied directly.

Blocker

You cannot own the spacebar

macOS has no supported way to replace Finder's Quick Look handler. Space will always be Apple's. Your entry points are double-click (register as default app for the image UTIs) and a global hotkey you claim yourself.

Spike needed

Finder sort order is reachable, awkwardly

Finder's AppleScript dictionary exposes the front window's selection and sort column. That's the path to trait 07 — but it needs an Automation permission prompt, and its reliability across view modes and macOS 26 is unverified. Prototype this before committing to it.

Design input

Sandbox vs. folder walking

Opening one file grants you that file, not its folder. To enumerate siblings you need security-scoped bookmarks for the parent directory — iMonet already does this. Or ship unsandboxed outside the App Store, which also frees the global hotkey.

Advantage

ImageIO is genuinely fast

CGImageSourceCreateThumbnailAtIndex pulls embedded previews without decoding the full RAW — the same trick FlyPhotos uses, but built into the OS. Format coverage (HEIC, RAW, AVIF) comes free. This is your trait-01 lever.

What I'd build

Swift + AppKit, not SwiftUI. A borderless NSWindow at screen level with a translucent backing is an AppKit primitive; SwiftUI fights you on window chrome and adds launch cost. Use SwiftUI only for the settings panel, if at all.

Render in Metal via CAMetalLayer or MTKView. Zoom-to-cursor is a texture transform, not a re-decode. This is what makes trait 04 feel right instead of laggy, and it's how you keep a 100 MP file smooth.

Three-tier load, mirroring FlyPhotos. On open: show the embedded EXIF thumbnail immediately (single-digit milliseconds), then a screen-resolution downsample, then the full decode only if the user zooms past fit. Preload N±2 on a background queue.

Attack trait 01 relentlessly. Your enemy is process launch, not decode. Keep the binary small, defer every framework you can, avoid dynamic-library loading at startup, and consider a resident helper process so the second launch is warm. Measure double-click-to-pixels, and treat 100ms as the bar.

Ship trait 07 as the wedge. Everything else on this list exists somewhere on the Mac. Finder-order fidelity doesn't, and it's the thing that makes the app feel like it belongs to the OS rather than sitting on top of it.

Skip for v1: editing, tagging, a library, face detection, cloud anything. Picasa-the-library is a different product and it's what killed every previous attempt at Picasa-the-viewer.

Build log · what measurement changed

The scaffolding is up and running against 36 MP test images. Seven findings came out of instrumenting it, and every one contradicted something reasonable-sounding. They are recorded in full in docs/performance-log.md; these are the ones that changed the architecture.

What was assumedWhat measurement showedEffect
Thumbnail API is cheap Without an explicit size cap it returns the image at native size. The "avoid decoding" call was decoding a 9000² JPEG in full. 1.05 GB → 307 MB
Max pixel size makes the decode cheaper It bounds the output, not the decode — the full 145 MB bitmap is still materialized, then resampled. True in JPEG as well as HEIC. kCGImageSourceSubsampleFactor is the flag that actually reduces the decode. JPEG 325 → 121 ms
Full-size decode is honest work CGImageSourceCreateImageAtIndex returned a 36 MP image in 1.3 ms because it is lazy. The decode reappears on the render thread. It also silently skips EXIF orientation. Removed a hitch and a rotation bug
Background preloading is free Neighbor decodes at low priority still compete for cores, stretching the image the user is waiting for from ~140 ms to ~390 ms. 2.8× on the foreground
A byte-ceiling cache bounds memory It drifted to 310 MB over a dozen navigations. Core Animation's GPU-side copies are invisible to byte accounting. Rewritten to bound by shape

Where it stands

Six of the seven traits are in, including the unclaimed one. Navigation — the interaction that actually dominates use — is 1 ms to first pixels, median over 40 steps, landing well inside a single frame. The image sharpens to full screen resolution ~190 ms later.

Trait 07 works. Finder exposes its sort order for list and icon views; column and gallery views expose nothing, and fall back to name order — which is also Finder's own default there. Two of four view modes, degrading sensibly, and more than any Mac viewer does today.

Cold launch is ~465 ms and remains the one number short of target. Memory regressed from ~120 MB to ~230 MB when the rail landed and is the open item.

Round two · seven more contradictions

Building the rail, trait 07 and the chrome produced another seven findings, and the pattern held: every one contradicted something that sounded obviously true. Two are worth repeating outside this project.

What was assumedWhat measurement showed
Background priority is enoughA dozen thumbnail decodes issued at once took 3.2 s each instead of 150 ms, and dragged the image the user was waiting for to 3259 ms. Priority decides who wins a scheduling contest; it does not reduce the number of contestants.
A view's layer is a view's layerSetting wantsLayer before assigning layer makes the view layer-backed: AppKit owns it and discards what you set. The backdrop had a correct frame and a correct colour and never drew. Fixed by deleting the view — a non-opaque window with a translucent background colour is the same effect in one line.
Cells can be keyed by indexAdopting Finder's order re-lists the folder underneath the rail, moving an image from slot 4 to slot 7 — so its thumbnail landed on the wrong cell and the current image was the one blank square. Anything cached against a position in a re-orderable list has this bug.
A file has one URLFinder hands over /tmp/photo.jpg; the folder scanner re-lists it as /private/tmp/photo.jpg. Both open fine, and every URL-keyed cache downstream then holds two keys for one photograph.
Testing permissions from a terminal is testing permissionsTCC attributes Automation consent to the responsible process. Launched from a shell the app inherits the terminal's existing right to control Finder and reports granted; launched with open -a the same binary correctly reports notDetermined. Ad-hoc signatures also change every build, so grants do not survive one.

Round three · formats, playback, three monitors

Format coverage is now a measurement rather than a claim. --selftest walks every file in a folder through the real decode ladder and reports pixels, frames, rung and timing, exiting non-zero on a regression. Current result on a 37-file corpus: 33/33 displayable · 2 animated · 2 video · 4/4 malformed rejected safely.

Three more findings

  • An undecodable file left the previous photograph on screen. Navigating onto junk painted nothing, so the old image stayed up under the new filename — which looks exactly like a file that opened fine. Found because the benchmark hung on it, not by looking.
  • Moving between displays of different density silently halves resolution. Nothing in the cache can detect it: the tier is unchanged and the bitmap is still valid for that tier. Dragging from the 1× 4K panel to the 2× built-in left the photo at 2294 px where it needed 2713 px, for as long as it stayed there.
  • The round-two memory regression did not survive scrutiny. Re-measured across three displays it is 111–136 MB, not 230 MB. The earlier figure was taken immediately after a synthetic hammer with decodes still unwinding.

Where it stands

Navigation is 3.7 ms to first pixels on a mixed folder and under 2 ms on 36 MP HEICs. The Retina panel is physically the smallest of the three displays and costs the most memory, which is correct — it has the most pixels. The portrait panel costs least, because the aspect-aware budget notices a square photo in a tall window is bounded by its width.

Cold launch, ~465 ms, remains the one number short of target.

Wishlist, from other people's issue trackers

Reddit blocks automated reading, so the better source turned out to be the issue trackers of the Windows viewers — those are wishlists, with reaction counts attached. What FlyPhotos users asked for, and what it shipped in response, is the closest thing to a validated feature ranking this niche has.

Two patterns stand out. The first is that almost every completed request is about chrome getting out of the way — fading controls, hiding the pointer along with them, click-a-thumbnail-to-jump. That is trait 02 being requested over and over in different words, which is reassuring for the wedge.

The second is that the loudest open requests are about formats and fidelity rather than interaction — HDR support is the top one. Worth noting for later: macOS has EDR, and a viewer that displays HDR photographs correctly on a Pro Display or a MacBook Pro panel would be a real differentiator that no Mac viewer currently claims.

  • Add to the trait list: pointer auto-hides with the chrome — currently the chrome fades and the cursor stays, which breaks the effect.
  • Add to the trait list: a delete shortcut that moves to Trash and advances, with undo. Repeatedly requested, and it is what turns a viewer into a culling tool.
  • Candidate, post-v1: HDR/EDR display. Top open request on FlyPhotos; unclaimed on macOS. All three attached displays report maxEDR = 1.0, so this needs hardware that can actually show it before it can be built honestly.
  • Done since: pointer auto-hide is still open; delete-to-Trash still open; copy image / copy path still open.
  • Candidate, post-v1: copy image, and copy path, from the viewer.

Loose ends

  • Attribute the 219 ms pre-launch gap. 56 ms is AppKit initialization; the remaining ~120 ms between will-finish-launching and the open-file event is unexplained. It is the whole obstacle to a sub-100 ms cold launch.
  • Try Pixea and SimpView for an hour each. My read on the commercial apps came from vendor copy and SEO roundups, not hands-on. SimpView especially may be closer than I've credited.
  • Decide App Store vs. direct early — it determines sandbox, global hotkey, and whether unsandboxed folder access is on the table. Direct distribution with Sparkle is the freer path; FlyPhotos does both and charges for the store build.
  • Naming. "PicasaPreview" can't ship — Picasa is Google's mark. Directions worth exploring: something from the lightbox/loupe vocabulary, or from the disposability idea (it appears, you look, it's gone).
